# 方案：通用 AI Agent 工作流与技能配置设计

- 日期：2026-10-23
- 状态：已完成（工作流与技能已落地；F-1～F-6 按建议值执行）
- 提出人：用户
- 关联文档：[AGENTS.md](../../../AGENTS.md)、[ai-models.json](../../../ai-models.json)、[tools/ai/README.md](../../../tools/ai/README.md)、[M0 执行计划](2026-10-22-m0-execution-plan.md)

## 1. 背景与目标

当前工作区已有「模型命名空间 + 计划/日志/缓存」规则（AGENTS.md），但缺少**可复用的工作流程**与**可加载的技能**：每个模型会话靠自由发挥，构建、测试、记录的规范没有固化。

目标：设计一套**模型无关**的配置，让任意模型（deepseek、kimi、后加入者）按同一套流程与技能工作：

1. 两条工作流：**规划**（产出计划）与**执行**（按计划实施）；
2. 三个基础技能：**模块构建**、**模块测试**、**工作日志**；
3. 构建技能的硬要求：组件内变量/函数必须有 Doxygen 标准注释；
4. 测试技能的硬要求：单元测试放 `<model>/ModuleTest/unit/`，集成测试放 `<model>/ModuleTest/integration/`；
5. 日志技能的硬要求：格式标准化；**提交与推送必须先征得用户同意**；多次未提交修改在获准后按顺序编号提交；
6. **语言规则**：所有代码注释（含 Doxygen）与 commit message **一律英文**；Markdown 文档（计划、日志、设计文档）与用户交流保持中文。

## 2. 总体设计

```
tools/ai/
├─ workflows/
│  ├─ planner.md          # 工作流 A：规划
│  └─ executor.md         # 工作流 B：执行
├─ skills/
│  ├─ module-build/SKILL.md
│  ├─ module-test/SKILL.md
│  └─ work-log/SKILL.md
└─ templates/             # 现有：plan / changelog / model-README
```

```
<model>/
├─ Temp/                  # 缓存（现状）
├─ Logs/{Plan,Log}        # 计划与日志（现状）
└─ ModuleTest/            # 【新增】开发期测试
   ├─ unit/<module>/      # 单元测试
   └─ integration/<scenario>/  # 集成测试
```

角色分工：

| 角色 | 输入 | 产出 | 不做什么 |
|---|---|---|---|
| 规划工作流 | 用户需求、现状文档 | `<model>/Logs/Plan/YYYY-MM-DD-<slug>.md` + 决策清单 | 不写业务代码 |
| 执行工作流 | 已确认的计划 + 决策 | 代码、测试、日志、提交 | 不擅自扩大范围 |
| module-build | 模块规格 | 源码 + 构建通过 + Doxygen 完整 | 不写测试 |
| module-test | 模块/场景规格 | `ModuleTest/**` + ctest 结果 | 不改产品代码逻辑 |
| work-log | 本次任务的事实 | 标准日志条目 + 提交/推送征询 | 不擅自 commit/push |

## 3. 工作流 A：规划（planner）

**触发**：用户提出方案/规划/设计/架构决策/路线图；或任务需要拆解。

**步骤**：

1. 读取上下文：AGENTS.md、相关 docs、`ai-models.json`、现状（git 状态、已有计划）；
2. 差距分析：现状 vs 目标，列缺口；
3. 落盘计划：用 `tools/ai/templates/plan-template.md`，状态 `planning`，含关联文档、验收判据、风险、决策项；
4. 自检：相对链接有效、任务可执行、验收可测量、决策项有建议倾向；
5. 输出：**计划摘要 + 待确认决策**，等待用户确认后进入执行。

**门禁**：计划文件不存在或缺少「执行记录/修订记录」→ 不得进入执行阶段。

## 4. 工作流 B：执行（executor）

**触发**：用户确认某计划（"按计划执行"），或指定具体 plan 文件。

**步骤**：

1. 读取计划与已关闭的决策，生成 todo 清单（每项含验证方式）；
2. 逐项实施：调用 **module-build** 建/改模块 → 调用 **module-test** 补测试；
3. 每完成一项：更新计划「执行记录」（日期 + 动作 + 结果）；
4. 全部完成后：调用 **work-log** 生成日志条目；
5. **征询**："是否提交？是否推送？"——未获明确同意不得 commit/push；
6. 获准后按 §7.3 的提交规则执行；
7. 汇报：交付物、验证证据（命令与结果）、未覆盖项。

**门禁**：任一项没有验证证据（构建/测试输出）→ 不得标记完成。

## 5. 技能 1：模块构建（module-build）

**输入**：模块名、语言（C/C++/Python/Rust）、目标目录、接口契约（能力 ID 或 C API）。

**步骤**：

1. 目录与构建接入（CMake `add_subdirectory` / 目标命名 `srsp_*`）；
2. 写声明（头文件/接口），**同步写 Doxygen**；
3. 写实现，**同步写 Doxygen**；
4. 构建：`cmake --preset <preset>` → `cmake --build`；
5. 静态检查：Doxygen 未文档化告警为 0、编译告警不新增；
6. 产出证据：构建命令、退出码、Doxygen 检查结果。

**Doxygen 规范（强制）**：

| 对象 | 要求 | 示例 |
|---|---|---|
| 文件 | `@file` + `@brief` | `/** @file plugin_host.cpp @brief Plugin loading and lifecycle */` |
| 结构体/类 | `@brief`，每个成员逐一说明 | `/** @brief Plugin instance */`；成员用 `///< description` |
| 函数 | `@brief`、`@param[in/out]`、`@return`/`@retval`、`@note`/`@warning` | 公共 API 必须完整 |
| 枚举/宏 | `@brief`；每个枚举值 `///<` | — |
| 语言 | **一律英文**：文件头、结构体、函数、枚举、行内注释（`//`、`///<`）全部英文 | 中文只出现在 Markdown 文档中 |

> 现状核对：`api/plugin_api.h`、`CMakeLists.txt`、`tools/ai/*.ps1` 的注释已是英文，规则与现状一致，不需要返工。

**验收**：构建通过；`doxygen` 配置 `WARN_IF_UNDOCUMENTED=YES` 时无告警；公共符号 100% 有注释；**注释语言检查：源码中不出现中日韩字符**（可用正则 `[\u4e00-\u9fa5]` 扫描 `.c/.cpp/.h/.hpp`）。

## 6. 技能 2：模块测试（module-test）

**目录约定（强制）**：

```
<model>/ModuleTest/
├─ unit/<module>/test_<feature>.cpp        # 单元测试
└─ integration/<scenario>/test_<flow>.cpp  # 集成测试
```

> 单元测试与集成测试都在**模型工作区**下（可按模型独立演进），不入 `Temp/`（Temp 会被清理）。

**用例要求**：

| 类型 | 范围 | 最低要求 |
|---|---|---|
| 单元测试 | 单个函数/类，依赖打桩 | 每个公共函数 ≥1 正例 + 1 反例；错误码路径覆盖 |
| 集成测试 | 跨模块（如 kernel+plugin、CLI+内核） | 1 条主流程 + 1 条失败路径；含确定性检查 |

通用规则：固定随机种子、禁止网络/墙钟依赖、单用例超时 ≤30 s、断言消息含上下文、以 ctest 注册（`add_test`）。

**与现有 `tests/` 的关系**：`tests/` 是工程级契约测试（ABI/schema/双传输），进 CI；`<model>/ModuleTest/` 是开发期测试，默认提交入库作为证据，单元测试进 CI、集成测试按需（nightly）。

**验收**：新测试全部通过；覆盖率不低于模块既有水平（核心模块目标 ≥70%）。

## 7. 技能 3：工作日志（work-log）

### 7.1 日志格式（唯一标准）

每次任务一条，写入 `<model>/Logs/Log/CHANGELOG.md`：

```
### V<n> — <一句话标题>

- 类型：<新增|修改|删除|重构|优化|文档|配置|修复>
- 文件：
  - `path/a`
  - `path/b`
- 摘要：<改了什么、为什么>
- 验证：<命令 + 结果；无法验证时写明原因>
- 关联计划：`<model>/Logs/Plan/YYYY-MM-DD-<slug>.md`
```

同日 `Vn` 递增；只写日期不写时间；优先用 `Append-ChangeLog.ps1`。

### 7.2 提交与推送的征询协议（强制）

1. **每次**修改后，向用户明确提问："是否提交？提交信息建议为 `...`；是否推送？"；
2. 用户未明确同意 → **不得** `git commit` / `git push`；
3. 用户只同意提交、未同意推送 → 只提交，推送前再问一次；
4. 征询时给出：变更文件清单、建议的提交信息、验证证据摘要；
5. 提交信息**一律英文**（与 AGENTS §4 一致），正文写清改动与验证。

### 7.3 多次未提交修改的批量提交

当存在 N 次独立修改且都未提交时：

1. 按**修改先后顺序**整理为 N 个提交（一次修改一个提交）；
2. 提交信息统一带序号：`(1/N) <scope>: <summary>`、`(2/N) ...`（英文）；
3. 每个提交对应一条日志条目（`V1..Vn`），最后附一条汇总说明；
4. 提交前把"提交计划"（N 条信息 + 对应文件）先给用户确认，再执行；
5. 推送同样先征询。

## 11. 风险与决策项

| 风险 | 说明 | 应对 |
|---|---|---|
| 技能与模型实际能力脱节 | 不同模型对 Doxygen/测试的遵守度不同 | 技能内含"验收命令"，由执行者自证 |
| ModuleTest 与 tests/ 职责重叠 | 两处都有测试 | 明确边界：契约测试归 `tests/`，开发期测试归 `ModuleTest/` |
| 提交征询打断自动化 | 每次都要问 | 允许"本次会话内批量提交一次"的授权，但推送仍逐次确认 |
| 目录膨胀 | 每个模型都有 ModuleTest | 只在有模块产出的模型下创建 |

| 编号 | 决策 | 建议 |
|---|---|---|
| F-1 | `ModuleTest` 是否按模块分子目录（`unit/<module>/`） | 是，便于定位 |
| F-2 | ModuleTest 是否提交入库 | 是（作为验证证据） |
| F-3 | 单元测试是否进 CI、集成测试是否 nightly | 单元进 CI；集成 nightly |
| F-4 | 是否用 `create_skill` 同步到 DSH 个人目录 | 是（跨仓库复用），仓库内文件为真源 |
| F-5 | 提交授权粒度 | 单次任务一次提交授权；推送逐次确认 |
| F-6 | 「英文注释」的边界 | 代码注释（含 Doxygen、行内、CMake/YAML/Schema 描述）与 commit message 用英文；Markdown 文档与对话用中文 |
