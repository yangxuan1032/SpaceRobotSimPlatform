# Skill：工作日志与提交协议（work-log）

> 职责：把一次任务写进 `<model>/Logs/Log/CHANGELOG.md`，并按规定征询后提交/推送。
> 硬规则：**提交与推送必须先获得用户明确同意**；**commit message 一律英文**；需要沙箱升级时**逐次申请**；**已执行的规划不入库**。

## 1. 触发

- 任何文件创建、修改、删除、重命名、移动；
- 构建、配置、脚本、文档结构调整；
- 任务结束、准备提交之前。

## 2. 日志记录

### 2.1 变更日志（CHANGELOG.md）

追加到 `<model>/Logs/Log/CHANGELOG.md`，同日 `Vn` 递增：

```markdown
### V<n> — <一句话标题>

- 类型：<新增|修改|删除|重构|优化|文档|配置|修复>
- 文件：
  - `path/a`
  - `path/b`
- 摘要：<改了什么、为什么>
- 验证：<命令 + 结果；无法验证时写明原因>
- 关联计划：`<model>/Logs/Plan/YYYY-MM-DD-<slug>.md`
```

要求：

- 只写日期，不写时间；
- 「文件 / 摘要 / 验证」三项不得省略；
- 优先用 `tools/ai/Append-ChangeLog.ps1`（自动编号）；
- 历史条目保留当时的路径，**不追改**。

### 2.2 问题与解决方案记录（ISSUES.md）

**位置**：`<model>/Logs/Log/ISSUES.md`（与 `CHANGELOG.md` 同目录，单文件，不拆分）。

**分工**：CHANGELOG 记「改了什么」，ISSUES 记「踩了什么坑、怎么出来的」。两者同一次任务可以各记一条，互相引用。

**触发**（满足任一即记）：

- 遇到非预期失败/报错并解决（构建、测试、git、环境、工具链）；
- 根因不明显的性能或行为异常；
- 需要绕过平台限制的临时方案；
- 修复过程改变了先前的设计或约定。

**格式**（同一天按先后顺序 `P1、P2……`，跨天从 `P1` 重新开始）：

```markdown
### P<n> — <一句话问题标题>

- 现象：<看到什么，含关键报错原文>
- 根因：<为什么发生，一句话说清>
- 解决：<怎么修的，含关键命令或参数>
- 验证：<命令 + 结果>
- 关联：`CHANGELOG.md` 的 Vn / 相关文件（可选）
```

**要求**：

1. 「现象 / 根因 / 解决 / 验证」四项不得省略；无法复现时写「未复现」并说明；
2. 现象里保留**原始报错关键行**（如 `Win32 error 5`、`unexpected eof while reading`），便于日后检索；
3. 解决要写**可复用的做法**，而不是"改了就好了"；
4. 只记录有复用价值的问题；一次性的笔误、闲聊、无结论猜测不记；
5. 已写入 ISSUES 的问题，若后续再次出现，追加新编号并引用旧编号（不追改旧条目）；
6. 提交前检查：本次任务是否踩坑？踩了就补一条 ISSUES，否则在提交说明中注明"无新问题"。

### 3.1 计划文件的版本编号（按天递增）

规划文件（`<model>/Logs/Plan/YYYY-MM-DD-<slug>.md`）的“修订记录”必须使用**当天顺序编号**，规则与 `CHANGELOG.md` 完全一致：

| 规则 | 说明 |
|---|---|
| 编号格式 | `V1`、`V2`……，同一天内按生成/修改的先后顺序递增 |
| 跨天重置 | 次日的计划文件重新从 `V1` 开始，不延续前一天 |
| 同一文件迭代 | 更新原文件并追加一行，编号顺延（不新建重复文件） |
| 多文件同日 | 同一天内多个计划文件各自独立编号（各自的 V1、V2），互不影响 |
| 禁止 | 跳号、重用编号、把日期写进编号（日期在文件头与表格中体现） |

**修订记录表格式**（必需三列）：

```markdown
| 日期 | 版本 | 说明 |
|---|---|---|
| 2026-10-26 | V1 | 初稿：问题、方案、里程碑 |
| 2026-10-26 | V2 | 增补 GPU 阶段与预留接口 |
```
## 3. 计划文件的 git 策略（新增）

**规则**：`<model>/Logs/Plan/` 只上传**未执行完**的规划；**已执行完的规划在提交时从版本库移除**。

| 计划状态 | 是否入库 | 提交时的动作 |
|---|---|---|
| `规划中` / `已确认` / `实施中` | 是 | 正常 `git add <plan>` |
| `已完成`（执行完毕） | **否** | `git rm <plan>`，在同一次提交中移除 |
| `已废弃` | 否 | 同上 |

判定依据：读文件头的 `- 状态：` 行，**只看状态关键字本身**（括号里的补充说明不参与判断）：

- `已完成` / `已废弃` → 应移出版本库；
- `规划中` / `已确认` / `实施中` → 保留入库。

例：`- 状态：实施中（环境与契约部分已完成…）` 属于**实施中**，不能因为括号里出现"已完成"就误删。

**例外（知识资产，始终入库）**：文件名含 `analysis` / `review` / `summary` / `landscape` 的分析、调研、摘要类文档——它们不产生可执行步骤，不作为规划移除对象。

**提交前必做检查**（PowerShell）：

```powershell
Get-ChildItem "<model>/Logs/Plan" -Filter *.md | ForEach-Object {
  if ($_.Name -match 'analysis|review|summary|landscape') { return }   # knowledge assets
  $line = (Select-String -LiteralPath $_.FullName -Pattern '^- 状态：' |
           Select-Object -First 1).Line
  if ($line -match '^- 状态：\s*(已完成|已废弃)') {                       # anchor: status keyword only
    $tracked = git ls-files --error-unmatch $_.FullName 2>$null
    if ($tracked) { "REMOVE FROM GIT: $($_.Name)  [$line]" }
  }
}
```

命中后执行：

```powershell
git rm "<model>/Logs/Plan/<plan>.md"     # 从版本库移除，历史仍可追溯
```

说明：

1. 移除后文件仍在 **git 历史**中（`git log -- <path>` 可查），不会真正丢失；
2. 若需在本地保留可读副本，先复制到 `<model>/Logs/PlanArchive/`（不纳入版本库）；
3. 本次日志的「文件」字段要列出被移除的计划，并在「摘要」说明「计划已执行完毕，按策略移出版本库」；
4. 禁止只 `git rm --cached` 后把文件留在工作区又再次 `git add`——这会让规则失效。

## 4. 临时操作权限申请（git）

### 4.1 两类权限必须分开

| 类型 | 含义 | 授予方 | 时效 |
|---|---|---|---|
| **A 业务授权** | 允许改历史：`commit` / `push` / `tag` / 改分支 | 用户文字同意 | 单次操作 |
| **B 沙箱执行授权** | 允许某条命令在更高权限下运行（DSH 的 `danger-full-access` 升级） | 用户在审批提示中确认 | 单条命令 |

A 是"能不能做"，B 是"环境允不允许做"；两者都要满足才能完成一次提交/推送。

### 4.2 可行性边界（DSH 机制）

- **可行**：DSH 支持对**单条命令**申请沙箱升级，需附理由，由用户在审批提示里确认；用户不确认则失败关闭（fail closed）。
- **不可行/不可假设**：
  - agent 不能自行授权，也不能把授权持久化；
  - 审批策略为 `never` 时，升级请求会被自动拒绝；
  - 不能绕过用户改审批策略，不能替换为"等效"的提权手段。
- 结论：B 只能**逐次申请**，A 只能**逐次询问**；拒绝后不得重试规避。

### 4.3 申请模板（提交/推送前必须给出）

```text
【申请临时操作权限】
操作：commit（N 个提交）/ push 到 origin/main
范围：<变更文件列表>
提交信息：<英文信息>
验证：<命令 → 结果>
需要沙箱升级：是 / 否（原因：<如 sh.exe 管道不可用、需网络凭据>）
授权时效：本次操作完成后失效
失败回退：保留工作区、不改历史、报告原因
```

### 4.4 常见阻塞与回退

| 现象 | 原因 | 处理 |
|---|---|---|
| `couldn't create signal pipe, Win32 error 5` | 沙箱禁止命名管道，`sh.exe`/凭据助手起不来 | ① 申请一次性升级后执行；② 或用 `GIT_ASKPASS` 临时注入凭据（用后立即清理） |
| 升级请求被拒 | 审批策略为 `never`、无应答方或用户拒绝 | 不自作主张；报告阻塞原因，请用户切换策略或手动执行 |
| 无可用凭据 | 未登录 GitHub / 凭据过期 | 提示用户配置；**不得**在命令、日志或文档里明文写 token |
| 推送被远端拒绝（非快进） | 远端有新提交 | 先 `fetch` 并报告差异，由用户决定合并方式，禁止 `--force` |

### 4.5 禁止事项（权限相关）

- 复用旧授权：上次同意 ≠ 本次同意；
- 用升级权限执行与 git 无关的操作；
- 在日志、命令回显或文档中记录 token / password；
- 因升级失败而改用其他方式绕过审批。

## 5. 提交前征询（强制）

每次准备提交时，向用户给出以下内容并等待回复：

```text
是否提交？
建议提交信息（英文）：<type>(<scope>): <summary>
变更文件：<列表>
按策略移出的已执行计划：<列表或"无">
验证摘要：<命令 → 结果>
是否需要沙箱升级：是 / 否（原因）
是否一并推送？
```

规则：

1. 未明确同意 → **不得** `git commit`；
2. 只同意提交、未同意推送 → 提交后停在本地，推送前再问；
3. 用户说"按你的判断"→ 仍需在提交前复述一次信息，得到确认后执行；
4. 被拒绝 → 保留工作区改动，不改写历史。

## 6. 多次未提交修改的批量提交

当有 N 次独立修改且都未提交时：

1. 按**修改先后顺序**排成 N 个提交（一次修改一个提交，不混装）；
2. 提交信息带序号，**英文**：
   ```text
   (1/3) feat(core): add plugin host loader
   (2/3) test(core): cover loader error paths
   (3/3) docs: record plugin host design
   ```
3. 每个提交对应一条日志条目（`V1..Vn`），最后可加一条汇总说明；
4. 执行前先把「提交计划」（N 条信息 + 文件归属）给用户确认；
5. 推送同样逐次征询。

## 7. 提交信息规范

- 格式：`<type>(<scope>): <summary>`，type ∈ feat/fix/docs/refactor/test/chore/build/config；
- 摘要用祈使句、≤72 字符、**英文**；
- 正文说明「改了什么、为什么、如何验证」；
- 不写中文、不写表情、不写无意义占位（如 `update`）。

## 8. 禁止事项

| 禁止 | 原因 |
|---|---|
| 未经同意 commit / push | 违反工作区规则 |
| 已执行的规划继续留在版本库 | 违反 §3 策略，历史冗余 |
| `--force` / 改写已推送历史 | 破坏他人基线 |
| 把多个不相关修改塞进一个提交 | 无法回溯 |
| 跳过日志直接提交 | 违反 AGENTS §3 |
| 提交信息用中文 | 违反语言规则 |

## 9. 产物

```text
<model>/Logs/Log/CHANGELOG.md 新条目
+ 经同意的提交（可选推送）
+ 已执行计划的移出记录（如有）
+ 授权与升级记录
```
