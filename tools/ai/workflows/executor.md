# 工作流 B：执行（executor）

> 适用模型：全部（模型无关）。输入是一份已确认的计划；输出是代码、测试、日志与提交。

## 1. 触发条件

- 用户确认某计划（"按计划执行"），或直接指定计划文件；
- 计划中的决策项已关闭，或用户同意按建议值执行。

## 2. 输入

| 输入 | 说明 |
|---|---|
| 计划文件 | `<model>/Logs/Plan/YYYY-MM-DD-<slug>.md` |
| 决策状态 | 哪些已确认、哪些按建议值 |
| 环境 | 工具链（preset）、`SRSP_AI_MODEL` |

## 3. 步骤

1. **读计划**：提取任务清单，为每项写「验证方式」；
2. **建 todo**：一项一条，含验收命令；
3. **实施**（逐项）：
   - 模块构建 → 调用 `skills/module-build`；
   - 补测试 → 调用 `skills/module-test`；
   - 每完成一项 → 更新计划的「执行记录」（日期 / 动作 / 结果）；
4. **回归**：跑受影响的构建与测试（至少一个 preset；跨工具链改动跑四端）；
5. **记日志**：调用 `skills/work-log` 生成条目；
6. **征询提交**：给出变更文件、建议提交信息（英文）、验证摘要，**等待用户同意**；
7. **提交/推送**：按 `skills/work-log` §4 的规则执行（未同意不得 commit/push）；
8. **汇报**：交付物、验证证据（命令 + 结果）、未覆盖项与原因。

## 4. 门禁

| 门禁 | 判据 |
|---|---|
| 无验证不完成 | 每项任务有命令级证据 |
| 不擅自扩范围 | 超出计划的需求 → 回到规划工作流 |
| 不跳过日志 | 有文件改动必须有 `CHANGELOG` 条目 |
| 不擅自提交 | 用户未明确同意 → 停在"待提交"状态 |

## 5. 失败处理

- 构建/测试失败：先定位（最小复现），修不了就**如实报告**并给出下一步选项；
- 环境受限（沙箱、网络、凭据）：记录现象与影响，不伪造通过；
- 计划本身有误：暂停并回到规划工作流修订计划（不静默改方向）。

## 6. 产物

```text
代码/测试改动 + <model>/Logs/Log/CHANGELOG.md 新条目 + 提交（经同意）
```
