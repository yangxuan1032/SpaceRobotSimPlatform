# 工作流 A：规划（planner）

> 适用模型：全部（模型无关）。输出唯一：一份可执行、可验收的计划文件。

## 1. 触发条件

- 用户提出**方案 / 规划 / 设计 / 架构决策 / 路线图**；
- 任务足够大，需要先拆解再实施；
- 已有计划需要修订（迭代同一文件，不新建）。

## 2. 输入

| 输入 | 来源 |
|---|---|
| 用户需求 | 当轮消息（原文要点，不臆测） |
| 工作区规则 | `AGENTS.md`、`ai-models.json` |
| 现状 | `git status`/`log`、相关 `docs/`、已有计划与日志 |
| 约束 | 语言规则、缓存目录、工具链矩阵 |

## 3. 步骤

1. **读上下文**：定位与需求相关的文档章节与代码位置（给出文件:行号）；
2. **差距分析**：现状 → 目标，逐项列缺口（缺什么、影响什么）；
3. **方案设计**：给出 2–3 个可选做法与取舍，选定一个并说明理由；
4. **落盘计划**：`<model>/Logs/Plan/YYYY-MM-DD-<slug>.md`
   - 用 `tools/ai/templates/plan-template.md`，或 `New-Plan.ps1`；
   - 必含：背景与目标、现状盘点、执行步骤（含验证方式）、交付物与验收、风险、决策项、执行记录、修订记录；
5. **自检**：
   - 相对链接全部有效；
   - 每个任务都有「完成判据」（可命令验证，不写"完成即可"）；
   - 决策项给出建议倾向；
6. **输出**：计划摘要（3–8 条）+ **待确认决策清单**，明确询问是否进入执行。

## 4. 门禁

- 计划文件不存在 → 不得进入执行；
- 缺「执行记录 / 修订记录」→ 视为未完成；
- 决策项未关闭 → 执行前必须确认（可标注"按建议值执行"）；
- 涉及删除/覆盖用户内容 → 必须在计划中单列并说明理由。

## 5. 产物

```text
<model>/Logs/Plan/YYYY-MM-DD-<slug>.md
```

交接协议：把计划路径与决策清单交给**执行工作流**（`executor.md`）。

## 6. 反模式

- 只给结论不给验收方式；
- 一次规划覆盖多个互不相关的主题（应拆成多份计划）；
- 把"待确认"写成默认已确认。
